Section 01

なぜファイルキューか

常駐セッション同士をどう繋ぐか。3案を比較して B を採用した。

Option Comparison

3案を比較しB を採用

案仕組み評価
A tmux send-keys 千葉が各ペインに直接プロンプト送信 即時だが割り込みが雑。作業中に競合
B ファイルキュー 採用 _shared/tasks/ に依頼 .md を置き各自が tick で拾う 疎結合・履歴が残る・dormant と相性良
C 千葉が単一窓口 Slack を千葉だけが受け Task ツールで子起動 常駐セッション方針と二重管理になり矛盾
採用理由： 動作主体を各エージェントセッションに置く方針と最も素直に噛み合う。誰が何を依頼・完了したかが監査ログとして残る。即時性が要る場面だけ A を後付けで足す。
Section 02

キューの構造

ステータスを物理ディレクトリで表現し、mv をロック代わりにする。

Queue Layout

ステータス＝物理ディレクトリ

~/agent/_shared/tasks/
├── inbox/ # 千葉が依頼を投函（担当未着手）
├── doing/ # 担当が着手時に mv（掴んだ印）
├── done/ # 担当が完了時に mv（結果を追記済み）
└── archive/ # 千葉が山下へ報告済みにしたもの
なぜ mv か： 同一ファイルシステム内の mv はアトミック。これがそのままロックになり、二重着手・取り合いを原理的に防ぐ。
Task File

タスクファイルのフォーマット

命名: YYYY-MM-DD-HHMMSS__<assignee>__<slug>.md

--- frontmatter ---
id: 2026-06-02-103000
assignee: ishikawa # kawakami / chiba / ishikawa / sato
from: chiba
priority: normal # urgent / normal / low
status: inbox
title: Focus for ADHD ティザー投稿の作成
-------------------

## 依頼内容 # 千葉が記述
## 完了報告 # 担当が完了時に追記（成果物URL・PR・所感）
Lifecycle

タスクのライフサイクル

inbox
千葉が担当を決めて投函
→
doing
担当が mv して着手宣言
→
done
完了報告を追記し mv
→
archive
千葉が山下報告後に mv
担当は __<自分>__ 宛のファイルだけを拾う。assignee がファイル名で固定されるため、別ペルソナが同じタスクを掴むことは起きない。
Per-role Tick

各ロールのtick 動作

千葉（オーケストレーター）

  • Slack/自判断でタスクを分解 → 担当を決め inbox/ に投函
  • done/ を巡回 → 山下へ集約報告 → archive/ へ
  • doing/ の滞留（24h超など）を監視

各員（川上・石川・佐藤）

  • inbox/ から自分宛を拾う（urgent 優先）
  • doing/ へ mv＝掴んだ宣言
  • 実行 → 完了報告を追記 → done/ へ mv
  • 自発タスク（lint修正等）はキュー外で実行してOK
Reporting Path

報告は千葉に集約

普段：千葉経由

  • 各員の「報告」は done/ への書き戻し
  • 千葉がまとめて山下へ Slack 報告
  • マネージャーが対外窓口になる

例外：名指し・緊急は直接

  • 山下が名指し DM した場合は当人が直接返信
  • 緊急時も当人が直接 Slack 返信OK
  • Slack 設定は _shared/COMPANY.md で全員保持
Edge Cases

即時性と夜間・衝突

即時性の補完（B の弱点対策）

  • B は tick 間隔ぶんの遅延が出る
  • priority: urgent のときだけ、千葉が投函後 tmux send-keys で「inbox確認して」と一言突く（A 併用）
  • 通常タスクは tick 待ちで十分

dormant / 衝突

  • JST 22:00–07:59 は誰も拾わない → inbox/ に溜め翌朝処理
  • assignee 固定 + mv のアトミック性で二重着手を防止
